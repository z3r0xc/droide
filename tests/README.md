# Tests

Acceptance tests for the reimplementation. A test exists to prove a spec clause,
not to describe the code.

## Rules

1. **One direction of mapping.** Every behavioural clause in `specs/*.md` maps
   to at least one test id, and every test names the clause it proves. A test
   that proves no clause is deleted or the spec is missing a clause.
2. **Deterministic.** Same input, same result, every run, on every supported
   platform. No ordering that depends on the filesystem, no unseeded randomness,
   no reliance on locale or timezone.
3. **No network.** No test opens a socket, resolves a name, or calls a service.
   Collaborators are replaced by in-process fakes or local files.
4. **No clock dependence.** Time is injected. Where a test needs a timestamp it
   supplies one explicitly; a test that would fail at midnight or on a leap day
   is broken. Same for process ids, hostnames, home directories, and temp paths:
   inject them, do not read them.
5. **Fixtures are synthesised.** Inputs are generated by our own code or written
   as literal text under `tests/fixtures/`. Never copy bytes out of
   `raw/factory/`, never commit an extracted bundle from `evidence/extracted/`,
   and never derive a fixture by running a vendor binary. A fixture built from a
   recovered artefact must be rewritten from the spec and labelled with the
   clause it exercises.
6. **Failures are clause failures.** A failing test names the clause id in its
   output so a red run points at a spec defect, an implementation defect, or an
   evidence defect — in that order of suspicion.
7. **No incidental assertions.** Assert the clause. Do not pin formatting,
   message wording, or internal call order unless the spec says they are part of
   the contract.

## Layout

```
tests/
  fixtures/          # synthesised inputs, one directory per area
  <area>/            # tests grouped by subsystem, mirroring specs/
```

Test ids are stable: renaming a test renames its references in the spec in the
same change.

## Running

The suite runs offline with a single command, documented here once the
implementation's toolchain is chosen. It must not require `raw/` to be present:
the tests prove the spec, not the extraction.
